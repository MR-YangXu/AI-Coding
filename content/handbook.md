# AI Code 项目操作手册

`@agent-xy/ai-code` 为 Vue 3 + Vite + TypeScript 项目提供 Cursor 编码规则，包括基础规则、九个通用技能，以及可选的管理后台和移动端 H5 场景。它也将项目已有的代码规则检查、类型检查、测试和构建统一到 `ai:check` 命令。

本手册供项目接入者、日常开发者和维护者使用。按下面的步骤，可以完成从接入、开发到验收、升级和故障恢复的完整流程。

> 本文件由 npm 包在 `init` 时生成到 `.ai-code/README.md`，在 `sync` 时更新。业务项目中请将长期约定写入 `.ai-code/profile.md`，不要直接修改生成的手册或规则；受控文件存在本地修改时，同步会拒绝继续。包源码中的 `content/handbook.md` 由包维护者更新。

## 1. 确认环境和项目位置

### 1.1 在业务项目根目录打开终端

后续命令都在业务项目的 `package.json` 所在目录执行。即使你正在阅读 `.ai-code/README.md`，也不要切到 `.ai-code/` 目录运行命令。

```bash
# 将路径替换为实际业务项目目录
cd /path/to/your-project
node --version
```

确认以下条件：

- Node.js 版本为 18 或以上，同时满足业务项目自身的版本要求。
- 项目已有 `package.json`，其中包含 `scripts` 对象。
- 项目已声明 Vue 3、Vite 和 TypeScript 依赖。`init` 用于接入现有项目，不负责创建 Vue 应用。
- 使用 Cursor 打开这个业务项目根目录。当前包提供 Cursor 适配，未提供其他 AI 编辑器的规则投影。

### 1.2 安装业务项目依赖

沿用仓库的包管理器，以下命令选一个执行：

| 包管理器 | 安装依赖       |
| -------- | -------------- |
| npm      | `npm install`  |
| pnpm     | `pnpm install` |
| yarn     | `yarn install` |

优先遵循 `package.json` 中的 `packageManager` 以及仓库锁文件。AI Code 初始化时依次按 `packageManager`、`pnpm-lock.yaml`、`yarn.lock` 判断包管理器，其余情况使用 npm。

如果仓库已包含 `.ai-code/config.json`，说明已经接入：安装依赖后直接进入第 4 步，不必再次初始化。

**本步完成条件：** 当前目录正确，Node.js 版本满足要求，业务项目依赖安装完成。

## 2. 初始化项目

### 2.1 首次接入：使用完整包名

```bash
npx @agent-xy/ai-code init
```

首次执行时，npx 可能提示下载包，按提示确认。随后 AI Code 会选择场景、安装自身的开发依赖、生成规则和配置，并增加 `ai:check` 脚本。

包名是 `@agent-xy/ai-code`，安装后提供的命令名是 `ai-code`。本手册后续的 `npx ai-code ...` 均以项目已安装该包为前提。未安装时请使用完整包名，避免 npx 按无作用域的 `ai-code` 包名查找其他包。

如果团队习惯先安装再初始化，也可以改用下面这一组命令；与上面的接入方式二选一：

```bash
npm install --save-dev --save-exact @agent-xy/ai-code
npx ai-code init
```

pnpm 项目第一条改为 `pnpm add --save-dev --save-exact @agent-xy/ai-code`，yarn 项目改为 `yarn add --dev --exact @agent-xy/ai-code`。已安装当前执行版本时，初始化不会重复安装该版本。

### 2.2 按提示选择场景和档案

首次在交互终端执行 `init` 时，先选择场景：

| 终端选项             | 对应参数          | 得到的能力                                         |
| -------------------- | ----------------- | -------------------------------------------------- |
| 不接入后台或 H5      | `none`            | 基础规则和九个通用技能                             |
| 管理后台             | `admin`           | 通用能力，以及搜索、表格、批量操作、权限和编辑流程 |
| 移动端 H5            | `mobile-h5`       | 通用能力，以及触摸、安全区、软键盘、滚动和弱网处理 |
| 管理后台 + 移动端 H5 | `admin,mobile-h5` | 安装两类场景，具体任务按实际功能选择使用           |

选择后台或 H5 后，还会询问是否按对应模板创建 `.ai-code/profile.md`。建议首次接入时创建，并在第 3 步核实和填写。选择“不接入后台或 H5”时，不再询问档案；需要通用档案时可用下一节的显式参数。

场景由开发者选择，不根据目录名或组件库自动推断。有搜索、列表或登录权限，不代表页面一定属于管理后台。移动端管理功能可以同时适用两个场景。

### 2.3 需要固定选择时，直接指定参数

以下都是首次接入方案，按项目选择一条，不要连续执行：

```bash
# 通用 Vue 项目，并创建通用档案
npx @agent-xy/ai-code init --scenarios none --profile vue

# 管理后台，并创建后台档案
npx @agent-xy/ai-code init --scenarios admin --profile admin

# 移动端 H5，并创建 H5 档案
npx @agent-xy/ai-code init --scenarios mobile-h5 --profile mobile-h5

# 混合项目，从通用档案开始补充各模块约定
npx @agent-xy/ai-code init --scenarios admin,mobile-h5 --profile vue

# 仅安装通用规则，暂不创建档案
npx @agent-xy/ai-code init --scenarios none --profile none
```

`--scenarios` 决定安装哪些场景技能；`--profile` 决定复制哪份档案模板。创建后台档案不会自动启用后台场景。

非交互环境、CI（持续集成）或使用 `--json` 时不会出现选择提示。首次接入未指定参数时使用通用场景、不创建档案；自动化接入应显式填写这两个参数。

### 2.4 核对初始化结果

以后台项目为例，成功时终端会显示：

```text
已接入 Cursor 规则和质量检查（观察模式）
项目场景：通用 Vue + 管理后台（admin）
项目档案：已按「admin」模板创建 .ai-code/profile.md，请替换其中的待填项并删除示例
```

未选择档案时不会显示第三行。检查项目中是否出现以下内容：

| 位置                                | 初始化结果                                                             |
| ----------------------------------- | ---------------------------------------------------------------------- |
| `package.json`                      | 增加开发依赖 `@agent-xy/ai-code` 和 `"ai:check": "ai-code check"` 脚本 |
| 包管理器锁文件                      | 正常安装依赖时记录对应包版本                                           |
| `.cursor/rules/ai-code.mdc`         | 默认加载的基础规则                                                     |
| `.cursor/skills/ai-code-*/SKILL.md` | 九个通用技能，以及选中的场景技能                                       |
| `.ai-code/config.json`              | 包版本、场景、检查模式、命令映射和受控文件记录                         |
| `.ai-code/README.md`                | 本操作手册                                                             |
| `.ai-code/profile.md`               | 选择模板且文件不存在时创建的项目档案                                   |

九个通用技能分别对应页面、组件、类型定义、常量与字典、Hook（组合式函数）、API（接口请求）、共享状态、路由和国际化。

`ai-code-type` 仅在新增、调整或审查类型定义、跨文件契约，或修复类型建模错误时读取；仅使用已有类型无需加载。它约定类型放置、复用、派生和外部值收窄，不强制每页创建 `types.ts`。类型设计规范由 AI 与审查落实，项目已有 `vue-tsc` 负责类型兼容性检查。

类型分为全局公共、业务局部和页面或组件局部。先查公共导出与当前业务入口，信息不足时按业务名称或符号定向搜索全项目，再按需读取相关定义与调用方；确认语义、归属及影响后停止。同一业务语义、同一契约只能有一份权威定义，使用处导入或派生，禁止换名复制及全局、局部重复维护。结构相同但语义不同的契约可分别定义；`vue-tsc` 不会自动拦截同义重复声明。

已有同名用户文件或 `ai:check` 脚本发生冲突时，初始化会报错，请按第 8 步处理。已有档案会原样保留。已接入项目重复 `init` 在配置正常时返回“已接入，无需修改”，不会重建命令映射或补建档案。

### 2.5 仅在需要跳过自动安装时使用 `--no-install`

```bash
npx @agent-xy/ai-code init --scenarios admin --profile admin --no-install
npm install
```

第二条按项目替换为 `pnpm install` 或 `yarn install`。`--no-install` 仍生成文件并写入依赖声明，只跳过 `init` 内部的安装动作；它不阻止 npx 为启动命令而下载包，也不保证整个过程离线。依赖真正安装完成后，才能运行本地 `ai-code` 和 `ai:check`。

**本步完成条件：** 所选场景正确，规则和配置已生成，依赖已安装。接下来填写项目档案。

## 3. 填写项目档案

### 3.1 找到或补建档案

打开 `.ai-code/profile.md`。如果文件尚不存在，从已安装包选择一份模板复制；以下以后台模板为例：

```bash
mkdir -p .ai-code
cp -n node_modules/@agent-xy/ai-code/content/templates/profile.admin.md .ai-code/profile.md
```

| 项目类型  | 模板文件               |
| --------- | ---------------------- |
| 通用 Vue  | `profile.vue.md`       |
| 管理后台  | `profile.admin.md`     |
| 移动端 H5 | `profile.mobile-h5.md` |

复制命令适用于 macOS/Linux；Windows 可以在文件管理器或编辑器中复制并重命名。`cp -n` 不覆盖已有文件。已有档案时直接编辑并合并需要的内容。

已接入项目不要依赖再次执行 `init --profile ...` 补建档案：当前实现会直接返回已有接入结果；`sync` 也不会创建档案。

### 3.2 根据源码填写推荐入口

档案由项目维护者填写，也可以明确委托 AI 核实后整理。依次完成：

1. 写清适用模块，例如哪些目录属于后台，哪些属于 H5。
2. 选择本项目实际存在、团队推荐的组件和组合式函数。
3. 对每项能力核实源码和至少一个已有调用方，记录可借鉴的部分。
4. 填写新页面的目录约定、公共与业务常量入口，以及需要避开的遗留实现。
5. 删除未填写、用不到的行、空章节和模板示例。

例如，下面展示的是填写格式，路径和名称需换成你已核实的项目内容：

| 能力与用途     | 源码入口                              | 已有调用方或参考页面         | 可借鉴部分与边界                               |
| -------------- | ------------------------------------- | ---------------------------- | ---------------------------------------------- |
| 后台搜索与筛选 | `src/components/SearchForm/index.vue` | `src/views/orders/index.vue` | 参考字段配置、提交和重置；订单字段及接口不照搬 |

路径相对项目根目录。组件属性、事件和接口字段仍以源码为准，不在档案里复制第二份契约。外部优秀页面可作为组织参考，但其中的组件、请求和工具必须在本仓库核实后才能导入。

混合项目可以从通用模板开始，合并后台和 H5 模板中适用的章节，并为每段标明模块范围。

### 3.3 明确哪些内容长期维护

| 内容                                   | 应维护的位置                |
| -------------------------------------- | --------------------------- |
| 推荐组件、参考页面、局部目录和团队约定 | `.ai-code/profile.md`       |
| 具体质量命令                           | `package.json` 的 `scripts` |
| 检查命令映射、检查模式、常量扫描配置   | `.ai-code/config.json`      |
| 本次需求、改动范围、验收结果和待联调项 | 当前任务说明或代码审查记录  |

档案不记录任务流水、密钥或真实用户数据。未填写的占位项不构成约定。更新档案后，新页面和新增常量按新约定组织；已有页面及常量文件不会因此自动迁移。

档案是可选的。没有档案时，AI 按基础规则参考一个相邻路由模块和一个同类页面，并在交付中说明约定缺口；日常页面任务不要求顺带创建档案。

**本步完成条件：** 已填写的入口真实存在、适用范围清楚；若暂不维护档案，团队明确当前采用相邻实现作为参考。接下来检查接入状态。

## 4. 确认接入状态和质量检查

### 4.1 查看状态，不执行质量脚本

```bash
npx ai-code status
```

核对输出的场景是否正确，以及是否出现规则版本不匹配、受控文件漂移或脚本缺失等提示。`status` 会检查配置、版本、受控文件和命令可用性；它不运行代码规则检查、类型检查、测试、构建，也不扫描常量源码。

某个只配置了 lint 的项目可能显示：

```text
项目场景：通用 Vue + 管理后台（admin）
lint: available (lint)
typecheck: missing
test: missing
build: missing
constants: not_configured
```

这里的 `available` 表示已找到可用命令，不表示已经执行通过；`missing` 表示当前映射没有可用命令。

### 4.2 执行一次项目级检查，了解初始状态

```bash
npm run ai:check
```

pnpm 项目执行 `pnpm run ai:check`，yarn 项目执行 `yarn run ai:check`。已安装包时，也可以直接运行 `npx ai-code check`。

该命令会执行 `.ai-code/config.json` 中映射的质量脚本；实际检查范围由这些脚本决定，通常包括整个项目。AI Code 不会替项目安装或重写 ESLint（代码规则检查工具）、TypeScript 或测试工具的配置。

| 状态                       | 含义                                                | 下一步                                |
| -------------------------- | --------------------------------------------------- | ------------------------------------- |
| `available`（可用）        | `status` 找到脚本，或常量配置结构有效；尚未执行检查 | 执行 `ai:check`                       |
| `passed`（通过）           | 对应检查已运行并通过                                | 继续核对其他检查和业务验收            |
| `missing`（缺失）          | 映射为空、脚本不存在或不符合自动检查要求            | 按下一节核对脚本和映射                |
| `failed`（失败）           | 已有脚本执行失败，或阻断模式下发现确定的常量违规    | 根据具体报错修复后重跑                |
| `not_configured`（未配置） | 尚未启用常量扫描                                    | 按需在第 9 步配置；不代表常量检查通过 |
| `warning`（警告）          | 常量检查发现需要处理或核对的问题                    | 阅读诊断，修复确定违规或核实疑似重复  |
| `incomplete`（未完成）     | 常量配置或扫描无法可靠完成                          | 修复配置、路径或解析问题后重跑        |

默认使用 `observe`（观察）模式：缺少质量命令不会单独导致退出码非零；已有脚本失败、受控文件漂移、版本不一致和无效配置仍会导致失败。因此，命令正常退出不代表所有检查都已经通过。

### 4.3 补齐脚本和映射

先查看 `package.json` 的 `scripts`，确认项目已有的检查命令。初始化按下列顺序选择每类的第一个可用脚本：

| 检查类别    | 自动识别的脚本名，按优先顺序                            |
| ----------- | ------------------------------------------------------- |
| `lint`      | `lint`、`lint:check`、`eslint`                          |
| `typecheck` | `typecheck`、`type-check`、`check-types`、`check:types` |
| `test`      | `test:run`、`test:unit`、`test`                         |
| `build`     | `build`                                                 |

带 `--fix`、`--write` 等修改型参数的脚本，以及未设置单次执行方式的 Vitest/Jest 测试脚本，不作为自动检查。需要时在项目中增加不改写源码、执行后会退出的专用脚本。

以补充类型检查为例：

1. 根据当前 Vue 与 TypeScript 配置，在 `package.json` 增加独立的 `typecheck` 脚本。常见写法是 `vue-tsc --noEmit`，实际参数和依赖版本需按项目确定。
2. 单独运行 `npm run typecheck`，确认它检查了预期源码；使用 pnpm/yarn 时替换命令入口。
3. 编辑 `.ai-code/config.json`，将 `scripts.typecheck` 设置为 `"typecheck"`，保留其他配置。
4. 再运行 `npx ai-code status`，预期显示 `typecheck: available (typecheck)`。
5. 运行 `npm run ai:check`，确认类型检查真实执行，并得到 `passed` 或具体失败信息。

例如，下面只是配置中的 `scripts` 片段，不要用它覆盖整个配置文件。值是 `package.json` 的脚本名，不是命令全文：

```json
{
  "scripts": {
    "lint": "lint:check",
    "typecheck": "typecheck",
    "test": "test:run",
    "build": "build"
  }
}
```

不存在的检查保留为 `null`。自定义脚本名也可手动映射，但仍须符合自动检查要求。`sync` 和重复 `init` 都不会重新发现后来新增的脚本，必须显式更新映射。

检查失败时，先区分检查配置错误、历史代码问题和本次新增问题。保留真实失败状态，不通过排除业务目录、使用 `any` 或忽略错误制造通过。构建通过也不能替代类型检查通过。

**本步完成条件：** 规则和版本一致；每项检查的通过、失败或缺失状态都有明确结论。没有接入错误时可进入开发；业务检查的历史缺口由团队安排处理，并在交付中保留说明。

## 5. 在 Cursor 中发起开发任务

### 5.1 准备任务信息

在 Cursor 中打开业务项目根目录，发起一个开发对话。基础规则配置为默认加载，相关技能按任务范围读取；例如修改后台页面时使用后台技能，同时改动路由时再读取路由技能，不需要每次粘贴所有规则。

开发者负责说明目标、修改范围、业务依据和验收条件。AI 按规则读取项目档案或相邻实现、核实组件与接口契约、实现并报告验证结果。本手册供人查阅，基础规则不要求 AI 在每次任务中读取它。

发起任务前准备以下信息：

| 信息     | 建议写法                                         |
| -------- | ------------------------------------------------ |
| 任务目标 | 新增哪个功能，或修复什么现象                     |
| 修改位置 | 实际页面、组件或业务模块路径                     |
| 输入依据 | 设计稿、已确认的接口文档、已有请求模块和参考页面 |
| 业务行为 | 搜索、重置、权限、失败反馈等具体预期             |
| 完成条件 | 哪些行为必须满足，是否包含真实接口联调           |

下面模板中的 `<...>` 都需替换为本项目内容；不适用的行直接删除。不要将示例路径或示例业务规则当成现有项目事实。

### 5.2 示例一：新增后台列表页

```text
请在当前项目新增订单列表页。

目标位置：<实际页面或模块路径>。
功能：关键词搜索、状态筛选、分页、查看详情。
设计依据：<设计稿或已确认的界面要求>。
接口依据：<已有请求模块或接口文档>。
参考页面：<本仓库实际页面路径>，只参考搜索和表格的接入方式。

验收要求：
- 提交搜索或重置后回到第一页。
- 重置后输入条件、已提交查询和列表结果一致。
- 请求失败时有明确反馈。
- 快速切换条件时，旧响应不能覆盖新结果。

按项目档案和已安装的相关技能实现，优先复用现有能力。
已有请求函数直接调用，字段不明标待确认、请求失败报错且不回退本地数据；仅在 URL 与请求函数均缺失且本次明确允许模拟时，按已确认契约使用可替换导入的 mock.ts，保持函数名、参数、异步行为和返回层级一致，禁止使用 demo.ts。
完成后说明改动范围、复用来源、实际检查结果及待联调项。
```

只有目标业务既无已确认 URL、也无现有请求函数，才属于接口未定。确需模拟时，在任务中明确写上“本次允许使用独立的 mock.ts 完成界面演示，真实接口待联调”，并提供已确认的函数与数据契约；未确认的部分标为待确认，不编造模拟契约。已有请求函数时，字段不明或请求失败都不能成为改用模拟数据的理由。AI 应继续完成不依赖待确认项的工作，并清楚标记演示范围。

### 5.3 示例二：修改已有页面

```text
请修改 <实际页面路径>，增加 <具体筛选项或交互>。

字段、默认值和接口依据：<已确认的契约或请求模块>。
本次范围：<需要调整的区域和关联文件>。
验收要求：<新增行为、失败处理和受影响的原有行为>。

沿用页面当前组织方式，复用已有组件与常量。
只修改本次需求涉及的部分，不迁移已有目录或重构无关逻辑。
完成后说明检查结果和未验证项。
```

### 5.4 示例三：修复问题

```text
请修复 <实际页面路径> 的 <问题现象>。

复现步骤：<可复现的操作顺序>。
当前结果：<实际发生的结果>。
预期结果：<正确行为>。
已知线索：<错误信息、相关请求或最近改动，没有则删除>。

定位触发条件后做必要修复，并核对原复现路径。
完成后说明原因、影响范围、实际验证方式和结果。
```

### 5.5 示例四：只做代码审查

```text
请只审查 <文件或本次改动范围>，不要修改代码。

需求依据：<对应需求和验收条件>。
重点：<本次关心的交互、接口、状态或复用问题>。

只报告有证据的问题，写明文件位置、触发条件和影响。
没有确认的问题时如实说明，不把推测写成缺陷。
```

### 5.6 核对 AI 的复用选择

正常任务中，AI 应依据档案或相邻实现核实推荐能力，再决定直接复用、兼容扩展或就近实现。关键事实不明确时，应提出具体缺口并继续不依赖它的工作。

若 AI 放弃现有组件或组合式函数，请核对它是否给出了以下依据；记录在当前任务中即可，无需新增文档：

```text
需求：当前交互必须满足什么。
候选：组件或组合式函数的源码位置及已有调用方。
能力与缺口：哪些已满足，哪些参数、分支或事件不匹配。
扩展评估：配置、插槽或最小扩展是否足够，会影响哪些调用方。
决定：直接复用、兼容扩展或私有实现，以及对应验证项。
```

“更贴近设计稿”或“直接写更简单”不能单独说明能力缺口。没有示例调用，也不能直接证明组件不支持。

**本步完成条件：** 需求和验收范围明确，AI 已完成相应实现，并提供可核对的改动、复用依据和验证结果。接下来由开发者验收。

## 6. 验收并交付本次改动

### 6.1 先检查改动范围

在编辑器或代码审查工具中查看差异，确认只修改了本次任务需要的内容。重点核对实际导入是否存在、接口字段是否有依据、公共能力是否重复实现，以及演示数据是否与真实业务隔离。

### 6.2 核对实际运行的检查

日常页面任务默认对本次改动文件执行项目已有的 lint（代码规则检查），具体命令按仓库配置确定。类型检查、测试和构建按改动影响、项目要求或本次任务要求执行，不默认每轮都跑全项目检查。

类型检查只在改动含类型边界，并且能把范围限制在新文件时运行。仓库级类型检查、构建和全量测试不是页面任务的默认步骤。没跑或失败不能写成通过，也不用别的命令互相顶替。

需要在提交或合并前执行项目级质量检查时，运行：

```bash
npm run ai:check
```

它与只检查改动文件的 lint 范围不同。若只想辅助识别本次改动新增的 ESLint 诊断，可按第 9 步使用 `quality inspect`。

检查失败后，根据具体位置修复，再运行相关检查。没有新变化或新问题时，无需反复扩大检查范围。没跑、没跑完和执行失败必须分别说明。

### 6.3 核对本次涉及的业务行为

沿用业务项目的启动命令，按需求中的验收条件检查。本包不会创建应用启动脚本。下面是后台页面的参考项，只选择当前页面实际具有的行为：

| 行为       | 操作                         | 预期结果                                       |
| ---------- | ---------------------------- | ---------------------------------------------- |
| 搜索和重置 | 修改条件并搜索，再执行重置   | 输入、已提交条件和结果保持一致；页码按需求重置 |
| 分页删除   | 删除末页最后一项             | 回到有效页或展示符合需求的空态                 |
| 启停操作   | 验证成功、重复点击和失败路径 | 不重复提交；失败保留原值或回滚，反馈明确       |
| 上传       | 选择符合及不符合契约的文件   | 合法文件正常处理，非法文件被拒绝并提示原因     |
| 异步查询   | 快速改变条件或切换详情对象   | 旧响应不会覆盖新结果，加载状态正确结束         |

H5 页面按实际需求增加触摸、软键盘、安全区、滚动或弱网检查，不套用不存在的后台交互。记录验证方式：代码路径核对、实际操作、自动测试或模拟响应；仅看过代码时，不写成已经实际操作通过。

### 6.4 查看一份合格的交付说明

下面展示报告格式，内容须替换为真实结果：

```text
已实现：<完成的功能及主要文件>。
复用来源：<参考页面、组件、组合式函数和常量入口>。
检查结果：<实际命令、检查范围、通过或失败情况>。
行为验证：<操作或代码核对方式，以及实际结果>。
未验证项：<未运行的检查、未覆盖的行为>。
待联调项：<尚未验证的接口和业务结果>。
```

只有模拟数据或内存状态变化时，交付应写“演示完成，真实接口待联调”；不能写成保存、删除或权限控制已经完成。接口补齐后，沿用同一组验收条件联调并更新结论，才能关闭对应待办。

### 6.5 将结果纳入团队交付流程

业务改动按团队流程提交或发起代码审查。首次接入和配置维护时，还应将依赖声明、对应锁文件、`.cursor/` 中本包生成的文件、`.ai-code/config.json`、本手册及已填写的档案纳入版本管理，便于其他成员获得相同配置；确认这些路径没有被仓库忽略。

其他成员拉取后安装依赖、运行 `status` 即可继续工作，不需要重复接入。检查通过不能单独证明 AI 遵守了所有规范，也不能替代业务验收。

**本步完成条件：** 需求范围内的实现经过审查，检查和行为结果有证据，未完成事项明确。若本次范围包含真实接口联调，应在联调完成后再标记任务完成。

## 7. 维护场景配置和版本

### 7.1 更换或增加场景

已接入项目通过 `sync --scenarios` 修改场景。下面选择一条执行：

```bash
# 改为仅管理后台
npx ai-code sync --scenarios admin

# 改为仅移动端 H5
npx ai-code sync --scenarios mobile-h5

# 同时启用后台与 H5
npx ai-code sync --scenarios admin,mobile-h5

# 回到通用规则
npx ai-code sync --scenarios none
```

然后确认：

```bash
npx ai-code status
```

`--scenarios` 替换完整选择，不是追加。原来启用后台时执行 `--scenarios mobile-h5`，后台会被取消；要保留两者必须同时写上。省略此参数时沿用 `.ai-code/config.json` 已保存的场景。

取消场景只移除受控清单中对应的技能文件，保留同目录的用户文件。受控文件有本地修改或新路径冲突时，先报错，不切换场景。

场景变化不会自动更新项目档案。同步成功后，检查 `.ai-code/profile.md` 的适用模块和推荐入口，按需手动补充对应模板内容。

### 7.2 升级 npm 包和项目规则

1. 查看当前改动，保留本地工作；运行 `npx ai-code status`，有冲突先按第 8 步处理。
2. 使用仓库包管理器安装团队确定的版本。下面的 `目标版本` 需替换为实际版本号，三条选一条执行。

```bash
npm install --save-dev --save-exact @agent-xy/ai-code@目标版本
pnpm add --save-dev --save-exact @agent-xy/ai-code@目标版本
yarn add --dev --exact @agent-xy/ai-code@目标版本
```

3. 同步新版本内容，然后检查状态和项目质量结果：

```bash
npx ai-code sync
npx ai-code status
npm run ai:check
```

最后一条按项目替换为 pnpm/yarn 的执行方式。只升级 npm 包还不够，必须执行 `sync` 才会更新业务项目已生成的规则、技能和本手册。

4. 如新模板增加了需要的章节，打开 `node_modules/@agent-xy/ai-code/content/templates/` 手动合并到 `.ai-code/profile.md`，保留已核实的本项目路径。
5. 审查并一起提交依赖、锁文件、生成文件和配置的差异。其他成员拉取后安装相同依赖并运行 `status` 确认一致。

`sync` 保留项目的检查模式、质量命令映射和常量配置，不覆盖档案，也不会重新识别检查脚本。需要回退时，优先恢复同一次已验证提交中的包版本、锁文件和配套规则配置，再安装依赖并检查状态；不要只回退其中一个文件。

**升级完成条件：** 安装版本与生成规则一致，档案仍保留项目约定，质量检查的变化已核对，相关文件一起进入版本管理。

### 7.3 更新团队约定

推荐组件、参考页面或目录约定变化时，直接编辑 `.ai-code/profile.md`，核实新路径并删除失效入口。仅修改档案无需运行 `sync`。

如果修改的是 `package.json` 中的检查脚本，同时检查 `.ai-code/config.json` 的 `scripts` 映射，按第 4 步运行相应命令验证。

### 7.4 从观察模式切换到阻断模式

先确保项目的 lint、类型检查和构建命令可执行，并处理团队决定必须解决的历史问题。然后只将 `.ai-code/config.json` 的 `mode` 从 `"observe"` 改成 `"enforce"`，保留其他字段，再执行：

```bash
npm run ai:check
```

`enforce`（阻断）模式要求 lint、类型检查和构建均存在；测试缺失暂不作为所有项目的强制阻断项，但已有测试失败仍会失败。启用常量扫描后，确定的常量违规也会阻断；仅疑似重复仍显示警告。

模式切换不需要 `sync`，选择后台或 H5 也不会自动切换模式。验证结果符合团队要求后，将配置变更一起提交。

## 8. 常见问题与恢复步骤

### 8.1 `ai-code` 找不到，或 npx 要下载另一个包

1. 确认终端位于业务项目根目录。
2. 查看 `package.json` 是否声明了 `@agent-xy/ai-code`，并按仓库包管理器安装依赖。
3. 首次接入使用 `npx @agent-xy/ai-code init`；已接入项目不要用重新初始化代替安装依赖。
4. 安装后运行 `npx ai-code --help`，预期看到 `init`、`sync`、`status`、`check` 和 `quality inspect`。

若使用过 `--no-install`，先补做依赖安装。

### 8.2 提示项目不受支持或配置不存在

提示缺少 Vue、Vite、TypeScript 或 `package.json` 无效时，先核对目录和第 1 步的环境要求。包不会将其他技术栈自动转换成支持的项目。

`status` 或 `sync` 提示无法读取 `.ai-code/config.json` 时：首次接入应先执行 `init`；已接入项目误删配置时，从版本管理恢复匹配的配置及文件，再检查状态。不要手写假的受控文件记录。

### 8.3 初始化提示同名文件或脚本冲突

1. 阅读报错中的具体路径或脚本名，确认原内容的用途。
2. 对用户原有的同名文件先做备份，将需要保留的团队约定迁到档案或项目文档，并把原文件移出将被生成的目标路径。
3. 若已有自定义 `ai:check`，将它改为合适的其他脚本名，并同步修改其原有调用方；清理冲突后再执行 `init`。不要让新旧脚本相互调用。
4. 初始化成功后运行 `status`，确认新脚本为 `ai-code check`，其他原有能力仍保留。

如果 `.ai-code/config.json` 已存在，应按现有接入项目处理，使用 `sync` 更新；不要删除配置来强行重新接入。

### 8.4 `sync` 提示“受控文件有本地修改”

这是生成文件的内容与记录不一致。同步在写入前检查冲突，有冲突时本次不会更新规则。按以下顺序恢复：

1. 根据报错定位文件，先保存其完整备份并查看差异。
2. 将需要保留的团队约定迁入 `.ai-code/profile.md`，普通说明迁入项目文档。
3. 将冲突文件恢复为当前受控记录对应的原内容；如果无法可靠恢复原内容，可以将已备份的冲突文件移出原路径，让 `sync` 重建缺失的受控文件。
4. 运行 `npx ai-code sync`，再运行 `npx ai-code status`。
5. 确认冲突提示消失、团队约定仍在，然后按团队流程保留或清理备份。

仅把内容复制到档案不会消除原文件的修改，必须完成第 3 项。不要修改 `config.json` 的 `managed` 校验记录来掩盖差异。

例如，只有 `.ai-code/README.md` 被手改时，先确认已提取需要的内容，再在 macOS/Linux 终端中执行：

```bash
backup_dir=$(mktemp -d)
mv .ai-code/README.md "$backup_dir/ai-code-README.md"
printf '原手册备份位置：%s\n' "$backup_dir/ai-code-README.md"
npx ai-code sync
npx ai-code status
```

临时目录用于本次恢复，需长期保留的内容另存到合适位置。其他冲突文件需按报错逐个处理，不要整体删除 `.cursor/` 或 `.ai-code/`。

若报错为“新规则与项目文件冲突”，说明该目标尚未被本包接管，但已存在用户文件。备份并移走该同名文件后重试。路径包含符号链接时，先核实并调整为本项目内的普通文件路径。

### 8.5 规则缺失、版本不一致或场景不一致

```bash
npx ai-code sync
npx ai-code status
```

`sync` 可以重建缺失的受控文件。版本不一致通常发生在安装新包后尚未同步；如果同时有本地修改，先按上一节恢复。

场景需要改变时使用 `sync --scenarios ...`，不要仅手动增删技能目录。恢复后的完成标准是版本、场景与受控文件一致，而不是仅看到命令退出成功。

### 8.6 明明有检查命令，结果仍是 `missing`

1. 检查 `.ai-code/config.json` 的对应 `scripts` 值是否为 `null` 或指向旧脚本名。
2. 确认 `package.json` 中有同名脚本，值填写的是可执行命令。
3. 确认脚本不带自动修复参数，测试使用单次执行方式，且没有反向调用 `ai:check`。
4. 将配置映射到合适脚本，单独运行后再运行 `ai:check`。

重新执行 `sync` 或 `init` 不会自动补齐映射。历史类型错误、构建错误按实际报错处理，不通过改成空脚本让检查显示通过。

### 8.7 AI 没有使用推荐组件或目录

1. 确认 Cursor 打开的是包含 `.cursor/` 的业务项目根目录。
2. 运行 `status`，确认规则和所需场景已经同步。
3. 检查 `.ai-code/profile.md` 中是否有真实路径、调用方及明确适用范围，是否仍只有“待填写”。
4. 在新任务中明确目标模块、参考入口和验收条件，核对 AI 实际引用的文件是否存在。
5. 对未复用的能力，要求给出第 5.6 节所列依据；确认是任务不适用、档案过时还是实现偏离，再修正相应内容。

`status` 验证安装和配置一致性，无法证明模型已读取或遵守每条规则。改进项目推荐入口应修改档案；需要改变所有项目共享规则时，由包维护者修改源文件并发布，再由项目升级和同步。

## 9. 按需启用进阶能力

### 9.1 配置常量与数据字典检查

所有场景都具备常量规范，但机器扫描需在 `.ai-code/config.json` 中配置 `constants` 后启用。未配置时，`status` 和 `check` 仍会返回 `checks.constants.status = "not_configured"`。

接入步骤：

1. 核实本项目已有的公共导出、业务常量和字典。相同业务语义只维护一份定义，不因数字相同就合并不同业务。
2. 查看包内 `node_modules/@agent-xy/ai-code/content/templates/constants/` 的完整示例。
3. 根据本项目真实路径和导出名改写示例中的 `constants` 配置，将这一节合并到已有 `.ai-code/config.json`，保留其余字段。
4. 运行 `npx ai-code status`。配置结构有效时常量状态为 `available`，此时尚未验证源码路径和定义。
5. 运行 `npm run ai:check`，核对诊断位置、确定违规和疑似重复；修复后重跑，确认扫描完成。

| 示例文件                | 用途                                   |
| ----------------------- | -------------------------------------- |
| `common.ts`、`index.ts` | 公共定义及统一导出的示例               |
| `business.constants.ts` | 业务模块常量与字典的示例               |
| `usage.vue`             | 页面导入、默认值、重置和选项的使用示例 |
| `config.json`           | 扫描范围、定义归属和字段绑定的配置示例 |

示例以订单业务演示，不能直接当成本项目接口契约。已有定义优先登记和复用，不覆盖重建。公共定义默认在 `src/constants/common.ts`，经 `src/constants/index.ts` 导出；业务定义位于所属模块的 `constants.ts`。档案另有约定时，新增定义以档案为准，并同步调整扫描配置。

配置中最常用的字段如下，路径均相对项目根目录：

| 字段                            | 填写内容                                                                                       |
| ------------------------------- | ---------------------------------------------------------------------------------------------- |
| `common.entry` / `common.files` | 公共导出入口及实际定义文件；使用公共定义时填写                                                 |
| `definitions`                   | 业务语义唯一 `id`、归属 `owner`、实际定义 `file`、导出名 `export`；同文件字典可填 `dictionary` |
| `modules`                       | 模块 `id`、扫描 `include`、可选 `exclude`，以及使用绑定 `bindings`                             |
| `bindings[].definition`         | 对应的业务语义 ID，只引用本模块或公共定义                                                      |
| `bindings[].fields`             | 字段或访问路径，例如 `status`、`query.status`                                                  |
| `bindings[].options`            | 选项变量名，例如 `statusOptions`                                                               |
| `bindings[].template`           | 模板组件 `component`、属性 `prop`，可选 `model` 限定 `v-model` 表达式                          |
| `tsconfig`                      | 路径别名所在的配置文件；默认读取存在的根 `tsconfig.json`                                       |

`include` 和 `exclude` 支持 `*`、`**`、`?`，不支持花括号匹配。同名字段含义不同时，缩小模块范围或使用更具体的访问路径。`definitions` 登记实际定义位置，不将转导出文件登记为定义来源。

检查结果的处理方式：

- 无问题时为 `passed`。观察模式发现违规时为 `warning`，应阅读并处理诊断。
- 阻断模式下，确定违规为 `failed`，退出码 1；只有疑似重复时仍为 `warning`。
- 无效配置、扫描范围没有文件、定义或语法无法解析等情况为 `incomplete`，两种模式都退出码 1。
- 一次最多展示五条诊断，同时给出总数；处理已列问题后重查。

扫描只读，覆盖已配置的定义和使用范围，不自动猜测所有字段归属，也不自动合并或删除源码。动态字典继续使用项目已有接口或服务，不登记为静态字典；静态扫描通过也不代表覆盖了所有运行时数据流。

### 9.2 查看本次改动的增量诊断

适用于已有有效 `HEAD`（当前提交）的 Git 工作区，且已安装项目 ESLint：

```bash
npx ai-code quality inspect
```

它检查相对 `HEAD` 已暂存、未暂存和未跟踪的 Vue/JS/TS 文件，使用当前工作区内容与历史内容的诊断结果比较。它不会自动修复源码，不需要接入配置，也不会修改 `.ai-code/config.json`。

| 结果                   | 含义与处理                                                     |
| ---------------------- | -------------------------------------------------------------- |
| `passed`（通过）       | 未识别到新增诊断；继续按需求完成其他验收                       |
| `failed`（失败）       | 有新增诊断，退出码 1；按位置修复后重跑                         |
| `incomplete`（未完成） | Git、ESLint 或历史基线无法可靠检查，退出码 1；根据提示修复环境 |
| `skipped`（跳过）      | 没有适用的改动文件；不等于已检查整个项目                       |

默认展示前五条新增诊断，并报告总数及是否截断。它是近似的增量比较，历史问题仍可能存在；规则配置变化、类型错误和跨文件影响需结合项目原有检查判断。

### 9.3 获取 JSON 报告并接入流水线

在本地查看结构化结果：

```bash
npx ai-code status --json
npx ai-code check --json
npx ai-code quality inspect --json
```

`npm run ai:check -- --json` 也会传递 JSON 参数，但 npm 可能在 JSON 前输出脚本横幅，不能把整段终端输出直接解析为 JSON。自动化需要纯 JSON 时，在已安装依赖且有本地二进制目录的环境中直接调用：

```bash
./node_modules/.bin/ai-code check --json
```

例如，在 macOS/Linux 流水线中保存报告并保留失败退出码：

```bash
if ./node_modules/.bin/ai-code check --json > ai-code-report.json; then
  cat ai-code-report.json
else
  check_exit_code=$?
  cat ai-code-report.json
  exit "$check_exit_code"
fi
```

报告使用流水线工作区或制品目录保存，不作为项目约定写回档案。`init --json` 的安装阶段仍可能输出包管理器日志，不按上述检查报告的方式直接解析。

Jenkins 等共享流水线的接入顺序：安装包含开发依赖的项目依赖 → 确认 `package.json` 声明了 `ai:check` → 使用仓库包管理器执行该脚本 → 保存结果并按退出码判定。不要在流水线中通过 `sync` 自动掩盖未提交的规则版本差异。

观察模式中的 `missing`、常量 `warning` 和 `not_configured` 需要如实展示；退出码为 0 不代表这些能力已经验证通过。若团队需要缺少必需检查就阻断，先按第 7.4 节启用阻断模式。

## 10. 命令与文件速查

### 10.1 常用命令

除首次接入命令外，下表以包已安装到当前项目为前提：

| 目的              | 命令                                                           | 使用时机                               |
| ----------------- | -------------------------------------------------------------- | -------------------------------------- |
| 首次交互接入      | `npx @agent-xy/ai-code init`                                   | 项目首次使用                           |
| 已安装包后初始化  | `npx ai-code init`                                             | 先安装依赖再接入                       |
| 指定后台和档案    | `npx @agent-xy/ai-code init --scenarios admin --profile admin` | 首次接入时固定选择                     |
| 查看接入状态      | `npx ai-code status`                                           | 接入后、拉取后或排障时；不执行质量脚本 |
| 执行项目质量检查  | `npm run ai:check` 或 `npx ai-code check`                      | 初次了解项目状态、集成验收或配置变化后 |
| 同步规则和手册    | `npx ai-code sync`                                             | 升级包后或恢复缺失的受控文件           |
| 同时启用后台与 H5 | `npx ai-code sync --scenarios admin,mobile-h5`                 | 场景范围变化时                         |
| 仅保留通用规则    | `npx ai-code sync --scenarios none`                            | 取消场景补充时                         |
| 增量代码规则诊断  | `npx ai-code quality inspect`                                  | 检查工作区改动相对当前提交的新诊断     |
| 查看帮助          | `npx ai-code --help`                                           | 核对当前已安装版本支持的参数           |

### 10.2 参数与边界

| 参数                                                  | 支持的命令     | 含义                                         |
| ----------------------------------------------------- | -------------- | -------------------------------------------- |
| `--scenarios none\|admin\|mobile-h5\|admin,mobile-h5` | `init`、`sync` | 完整的场景选择；不要将表中的竖线作为命令内容 |
| `--profile vue\|admin\|mobile-h5\|none`               | `init`         | 首次接入时创建指定档案模板，已有文件不覆盖   |
| `--no-install`                                        | `init`         | 跳过命令内部安装，仍写依赖声明和接入文件     |
| `--project <目录>`                                    | 全部命令       | 指定目标业务项目根目录，默认是当前目录       |
| `--json`                                              | 全部命令       | 输出结构化结果；首次初始化不进行交互询问     |
| `--help`                                              | 全部命令       | 显示帮助                                     |

例如，使用当前可用的包检查另一个项目：

```bash
npx @agent-xy/ai-code status --project /path/to/your-project --json
```

该命令使用的是本次实际执行的包版本；日常检查优先在目标项目根目录调用本地安装版本，避免不同版本间产生不匹配提示。带空格的项目路径需用引号包裹。未知参数、无效场景或档案名称会报错，不会静默回退为默认值。

### 10.3 哪些文件可以修改

| 文件                                | 维护方式                                           | `sync` 的行为                                  |
| ----------------------------------- | -------------------------------------------------- | ---------------------------------------------- |
| `.cursor/rules/ai-code.mdc`         | 包维护，项目中不手改                               | 核对本地改动后更新                             |
| `.cursor/skills/ai-code-*/SKILL.md` | 包维护，项目中不手改                               | 更新通用及选中场景，移除取消的受控场景文件     |
| `.ai-code/README.md`                | 包维护，项目中不手改                               | 随包更新                                       |
| `.ai-code/profile.md`               | 项目维护推荐入口与约定                             | 不创建、不覆盖                                 |
| `.ai-code/config.json`              | 项目维护模式、命令映射和常量配置；场景通过命令调整 | 更新版本、场景及受控记录，保留已有项目检查配置 |
| `package.json` 与锁文件             | 项目维护依赖和实际脚本                             | `sync` 不安装依赖、不修复脚本                  |

受控文件是本包生成并记录内容校验值的文件。`packageVersion`、`schemaVersion` 和 `managed` 等记录由工具维护；团队约定放入档案后，通过“修改 → 执行相关检查 → 核对结果 → 提交配套文件”完成维护。
