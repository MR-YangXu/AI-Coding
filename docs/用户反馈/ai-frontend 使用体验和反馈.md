## 2. ai-frontend 插件使用情况速览

- 定位清晰：按技术栈生成 Cursor 规则和技能、维护 `.ai-code/profile.md` 团队档案、复用项目已有 lint/typecheck/build 做质量门禁，外加只读常量扫描。
- 架构分层清楚：`content/` 放规则文本，`src/stack.mjs` 管技术栈，`src/project.mjs` 管配置与同步，`src/check.mjs` 与 `src/quality.mjs` 分别做全量检查与增量 ESLint，`src/constants/` 做常量扫描。
- 受控文件策略明确：插件生成文件 sync 覆盖，团队约定只写 `profile.md`，升级不丢团队内容。

## 3. 插件需要优化的地方

1. `check.mjs` 的全量检查直接继承项目脚本的输出噪声。M-front 全量 `lint` 有 5576 个历史错误，AI 按规则只看改动文件是对的，但插件侧缺一个「只看增量」的默认推荐路径，容易让用户误以为全量失败就是本次改动的问题。
2. `quality.mjs` 的增量检查依赖 Git HEAD 和项目 ESLint；在无 HEAD、无依赖或 ESLint 缺失的新项目里会直接抛错，建议在 `status` 里提前给出可操作的安装或初始化提示。
3. `spawnSync` 的质量命令没有超时兜底。`quality.mjs` 的 git/eslint 调用有超时，但 `check.mjs` 执行 lint/typecheck/build 时 `maxBuffer` 设了 8MB 却没设超时，遇到卡住的项目脚本会一直挂起。
4. `sync` 恢复漂移文件时直接覆盖，没有先备份或先展示 diff。规则文件本身可再生问题不大，但用户在排查「为什么我的修改丢了」时缺少一次确认或回滚线索。
5. 规则文本里「不派子代理」「不读 docs」这类约束是写给 AI 的，但插件没有给人类一个对应的解释入口；新成员第一次看到规则被覆盖时容易困惑，建议在 `.ai-code/README.md` 里加一段人类可读的说明。
6. `config.json` 的 scripts 映射是 init 时快照的，项目后续新增或改名脚本后只能手动改。建议 `status` 在发现疑似新脚本时给出提示，而不是静默沿用旧映射。

## 4. 生成的代码发现的问题

以 M-front 实际生成物为证据：

1. 复制逻辑与 `src/utils/clipboard.ts` 重复。工具函数已存在且被多个页面复用，本次在 `columns.ts` 里重写了一套成功/失败提示，只是为了满足「失败提示重试」的文案。更好的做法是给 `handleClipboard` 加可选的失败文案参数，而不是复制一份 Clipboard 生命周期管理。
2. `ClipboardJS` 类型缺失 `onClick`，生成代码用了 `as unknown as { onClick... }` 收窄。能通过类型检查，但属于局部补丁；长期应在项目内补一个 `clipboard.d.ts` 或统一封装，而不是每个调用点各自断言。
3. 订单表列宽从 150 改为 200 是硬编码的布局补偿，没有验证窄屏或长订单号是否仍然溢出。表格列宽在项目里本就不统一（profile 已记录待统一），这次改动又新增了一个特例。
4. 插件生成的 `profile.md` 初始模板里有大量「待人工确认」条目，M-front 的档案至今仍是「待人工审查」状态。模板把判断责任推给了团队，但没有给「确认后删掉这行」的闭环动作，档案容易长期停在草稿态。

## 5. 建议可以扩展的方向

按投入从小到大：

1. 增量检查设为默认推荐：`ai:check` 保持全量门禁不变，但文档和 `status` 输出里主推 `quality inspect`，让日常 AI 任务默认走增量。
2. 常量扫描结果接入档案：扫描发现的重复定义或归属问题，可选写回 `profile.md` 的常量章节，而不是只在终端输出一次。
3. 依赖治理方案值得做：与常量扫描同架构，复用 check 调度，解决 banned import、循环依赖、license 违规三类不可逆问题。
4. 给 `sync` 加 `--dry-run` 和备份：先展示将要覆盖的文件 diff，可选保留 `.bak`，降低用户对「覆盖」的戒心。
5. 规则版本与项目版本的对应表：`config.json` 已记录 `packageVersion`，建议 `status` 输出一行人类可读的变更摘要（新增技能、删除技能、规则大改），而不是只提示「不一致请 sync」。
