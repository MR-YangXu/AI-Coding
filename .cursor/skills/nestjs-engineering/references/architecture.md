# 模块、依赖与请求链路

适用：新增模块、排查注入失败、抽取横切逻辑、更换 HTTP 适配器、调试启动和请求问题。课程主题：第 1—24、104、141、200 章。

## 模块与 Provider

先画出直接依赖：哪个入口调用哪个服务，哪个模块注册并导出了该服务，消费者是否导入该模块。`@Injectable()` 不会替代 `providers` 注册；类也不是因为写了装饰器就自动成为全局依赖。

| 实际需要 | 注册方式与检查 |
| --- | --- |
| 常规可注入实现 | 类 Provider；核对依赖是否在模块作用域可见 |
| 配置值、已有外部对象、测试替身 | `useValue`；确认对象生命周期及是否允许共享可变状态 |
| 根据配置创建连接或异步资源 | `useFactory` + `inject`；等待初始化成功，失败不能伪装为已就绪 |
| 为已有实例提供别名 | `useExisting`；不额外创建第二个连接池或状态实例 |
| 按环境选择实现 | `useClass`；保持服务契约一致 |

外部连接使用稳定的 class、symbol 或常量 token（注入标识）；注册端和注入端必须使用同一标识。已有项目使用属性注入时保持一致，新代码通常使用构造器显式表达依赖。

全局模块只用于明确的公共基础设施，并仍需在入口导入一次。不要用 `@Global()` 掩盖错误的模块依赖。动态模块的 `register/forRoot/forFeature` 是约定命名，是否复用实例取决于具体实现和导入方式，不要假定方法名本身保证“只注册一次”。

出现循环依赖时，先核对是否双向承担业务职责、是否由 barrel（聚合导出）文件引入循环。能通过共享较小服务或调整调用方向消除时先调整；确实需要双向依赖才按当前 Nest 版本在对应两端使用 `forwardRef`。不要依赖循环双方构造顺序，也不要在构造器中调用尚未就绪的对方。

## 生命周期与资源

数据库、Redis、消息客户端等资源由创建它的 Provider 管理。初始化成功后才提供服务；关闭时停止接收新工作、等待在途任务至约定期限，再释放资源。根据平台配置应用关闭钩子并验证终止信号。

区分默认单例、请求作用域、临时作用域；请求作用域可能沿依赖链传播，不能把请求用户放在共享单例的可变字段中。生命周期细节按作用域和版本核对，不假设所有 Provider 都会收到同样的关闭回调。

## 请求链路选择

HTTP 成功路径通常为：Middleware（中间件）→ Guard → Interceptor 前置部分 → Pipe → Controller/Service → Interceptor 响应部分。多个拦截器的响应阶段按嵌套关系返回；异常会改变正常流程，Filter 不是每次请求必经的最后一步。

| 要处理的问题 | 适合的位置 | 不要混淆 |
| --- | --- | --- |
| 请求关联标识、通用协议预处理 | Middleware | 通常不能据此读取目标 handler 的业务元数据 |
| 登录、权限、资源访问条件 | Guard 或有清晰授权职责的业务服务 | 前端路由拦截不能替代服务端授权 |
| 参数解析、格式和结构验证 | Pipe | 结构合法不代表允许操作该资源 |
| 响应映射、耗时、通用超时 | Interceptor + RxJS | 不统一包装文件流或 SSE；超时也不等于底层任务已取消 |
| 未处理异常到协议错误的映射 | Filter | 不吞异常后返回成功状态；处理未知异常时隐藏内部信息 |

需要注入服务的全局扩展通过 `APP_GUARD/APP_PIPE/APP_INTERCEPTOR/APP_FILTER` 注册。若选择 `app.useGlobal*`，检查实例来源及依赖是否已由容器构建。

装饰器应表达稳定含义；重复组合可用 `applyDecorators`，参数提取可用 `createParamDecorator`。元数据键集中定义。使用 Reflector 时明确方法覆盖类配置还是合并两者，再选择对应读取方式。

HTTP、RPC（远程调用）、WebSocket、GraphQL 的上下文不同。先确认 `ExecutionContext` 类型，再通过对应适配器读取用户和请求；不要在通用守卫中无条件调用 `switchToHttp()`。GraphQL 需要相应的上下文转换。

## CLI、适配器与调试

CLI（命令行工具）生成前检查已有目录、路径别名及测试约定；先查看生成差异再补业务，不把演示脚手架覆盖到现有模块。Monorepo（单仓多项目）与微服务部署是不同决策，共享库只承载真正共享的契约或基础设施。

切换 Express/Fastify 前检查上传组件、Session、中间件、响应对象和异常处理等依赖。切换适配器不能只改 `NestFactory` 参数；基于 Multer 的 Express 上传不直接适用于 Fastify。

调试先使用项目已有启动脚本、source map（源码映射）、条件断点和调用栈。REPL 适合隔离检查 Provider，端到端行为仍经真实协议入口测试。需要调试 Nest 源码时匹配实际版本，在隔离环境构建映射和调试配置，避免直接覆盖日常工作区的 `node_modules`。

验证：应用可启动、依赖实例数量符合预期、跨模块导出可见、失败路径与钩子顺序正确、终止后连接释放。没有适配器切换的实际验证，不声明两种适配器均兼容。
