# 身份、权限与会话

适用：注册登录、验证码、JWT/Session、权限、第三方账号与扫码登录。课程主题：第 66—75、81、89—90、103 章及各实战认证模块。

## 明确会话模型

核对客户端类型、跨域情况、会话有效期、注销/冻结策略、并发设备和存储方式。Session 服务端保存状态，JWT 通常携带签名声明；JWT 的签名不加密内容，不能放密码或秘密。

Cookie 是否存在 CSRF（跨站请求伪造）风险取决于浏览器是否自动携带凭据；JWT 放在 Cookie 里也可能有此风险。浏览器可读存储则需要考虑 XSS（跨站脚本）导致的令牌泄露。按既有方案配置 HttpOnly、Secure、SameSite、CSRF 防护和严格跨域允许列表，不把某一种存储位置写成普适最优解。

密码采用适合密码的加盐哈希算法及项目批准的参数，禁止明文或直接 MD5/SHA 摘要保存。登录错误避免暴露不必要的账号存在信息，配合限流。注销、重置密码和冻结后，按会话模型撤销会话或更新可验证的版本/撤销状态。

## 认证与授权分别验证

Guard 验证凭证后建立可信请求用户；服务端通过该身份判断资源所有权、租户和角色权限。不要信任请求体里的 `userId`、`role`、`isAdmin` 或前端隐藏按钮。

ACL（访问控制列表）与 RBAC（基于角色的访问控制）按业务选用。权限存储、元数据及 Guard 使用同一权限标识来源，未知权限默认拒绝。区分未认证 401 和已认证但无权 403。权限缓存必须有失效方案，冻结账号不能仅等长效令牌自然过期。

Passport 负责组织 Strategy（认证策略），`validate` 成功建立身份，不代表已经完成业务授权。自定义策略异常映射和凭证日志要保持一致。

## 令牌刷新

JWT 校验签名、允许算法、有效期及项目规定的 issuer/audience（签发者/受众）。Refresh token（刷新令牌）不能被普通业务接口当成 access token（访问令牌）；使用类型/用途声明、独立验证配置或其他明确区分。

采用双令牌时：访问令牌短时有效；刷新令牌检查服务端会话与用户状态，按协议轮换并处理重放。刷新失败让所有等待请求退出，清理会话并进入登录流程。前端使用单个共享刷新 Promise/队列，阻止并发 401 各自刷新；排除刷新接口本身，标记最多一次重放，避免无限循环。非幂等请求是否可重放需依据服务端契约和幂等键判断。

采用单令牌滑动续期时：临近到期才续签，保留会话绝对最长寿命、撤销检查及并发响应顺序控制。不能让迟到响应覆盖更新的凭证。通过自定义响应头返回新令牌时，核对 CORS 的 exposed headers（允许前端读取的响应头）。

第 72 章作者已注明示例应改为临近过期续期；第 159、178 章相关演示不能据此当成完整生产会话策略。

## 邮箱验证码与密码重置

验证码绑定用途、账号/邮箱、有效期和必要的挑战标识。使用安全随机值，服务端限制发送频率、验证尝试和总有效期；根据需求保存验证码哈希。避免日志记录验证码。

同一个验证码的检查和消费需原子化，两个请求不能同时通过。消费与数据库变更跨存储时明确失败重试策略，避免不可恢复的半完成状态。修改邮箱需要验证相关身份和新地址，不能只验证请求者任意提交的邮箱就修改其他账号。

密码重置不要求旧登录态时，重置凭据就是认证依据，应绑定正确账号、限制尝试、一次使用并撤销必要旧会话。前端按钮倒计时仅用于体验，不能替代服务端限流。

## OAuth 与扫码

第三方登录使用官方策略及已登记回调地址，验证 `state` 防止回调混淆；适用时使用 PKCE，OIDC（开放身份连接）还需校验 ID token 和 nonce（一次性关联值）。以稳定的提供方用户 ID 绑定账号，不仅凭可修改昵称或未经验证邮箱自动合并账号。

回调不在 URL、日志或不必要的前端可读 Cookie 中暴露长效凭证。若需跨端同步，用短时一次性交换码或符合现有会话模型的安全 Cookie；失败和取消授权也必须有确定状态。

扫码登录使用不可预测挑战 ID、短 TTL，以及待扫码→已扫码→已确认/已取消/已过期的合法状态转换。确认方必须已认证，桌面端绑定自己的挑战并仅能领取一次结果；扫码本身不等于确认登录。轮询有间隔、超时和退出清理。

验证：无凭证、伪造/过期/错用途令牌、并发刷新、刷新失败、注销和冻结、跨用户操作、验证码重复消费、OAuth 错误 state、二维码过期与重复领取。
